## 事件摘要

Phase 63 後，TASK_HISTORY.md 超過 4000 行，每次對話初始 token 消耗約 135K。  
Phase 64 設計並落地「四層防線」，將每對話 token 消耗降至 ~820 tokens（節省 **98.8%**，原估 92-96%，實測更優）。  
Phase 64.1 進一步補強，加入 G5-1 規則退化警示、hook 測試覆蓋、ADR 等 7 項追溯優化。

---

## 什麼做對了

### 1. 多層冗餘設計（Defense in Depth）
不依賴單一機制，四層防線各自獨立失效。事後用 v3.0 框架回溯診斷，四層設計通過 X4（多角色審查）與 G4-1（量化決策）驗證。

**通則化**：高重要性的「禁止行為」應設計成多層冗餘，而非單點規則。

### 2. 環境最小化（Minimal Footprint）
四層防線全部使用已有工具（settings.json hook + CLAUDE.md + MEMORY.md + 文字），零新依賴、零新框架。

**通則化**：優先使用現有機制做延伸，不為了「優雅」引入不必要的依賴。

### 3. 量化驗收（不靠主觀感受）
落地後主動設定 token 節省率（92-96%）作為量化驗收指標，而非「感覺好多了就算」。

**通則化**：每個效能優化 Phase 落地後，必須設定至少一個量化指標作為驗收基準。

### 4. 計畫書先行（草案共核制）
Phase 64 設計草案在主公核准後才動工，避免了兩個被棄選方案（拆分/摘要）的陷阱。

**通則化**：凡影響「核心協議」（存檔協議、編年史主權）的變更，必須計畫書先行。

## 什麼可以更好（Phase 64.1 補強的原因）

### 1. 缺 G5-1 規則退化警示（**致命缺口**）
四層防線如果 90 天後沒人確認還在運作，會默默腐爛。Phase 64 沒有設計「健康確認」機制。  
→ Phase 64.1 補入 `scripts/rule-decay-check.sh` 解決此問題。

### 2. 缺 hook 測試覆蓋
Hook scripts 改好後沒有自動化測試守護。如果後來有人改壞，不會有任何提示。  
→ Phase 64.1 補入 `tests/test_hooks/` 4 個測試腳本。

### 3. 缺 ADR（架構決策記錄）
為何選四層而非其他方案？原始草案在對話紀錄裡，沒有提取成永久文件。  
→ Phase 64.1 補入 `docs/adr/001-four-layer-defense-rationale.md`。
