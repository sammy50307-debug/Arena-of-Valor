# Postmortem — P70.3 LINE 滑動失靈

- **日期**：2026-05-08
- **影響**：P63.2 至 P70.3 期間（約 5 週），所有 LINE in-app browser 開啟的報告完全無法垂直滑動
- **嚴重度**：B（功能性 UX 損壞，但桌面 / 一般行動瀏覽器不受影響）
- **作者**：Sonnet 4.6（主公審核）

---

## 一、症狀

主公在 LINE 中點開報告連結後：
- 整頁觸控滑動失效（手指上下滑無反應）
- 桌面瀏覽器、一般 Chrome / Safari 行動版均正常
- 跨多個歷史報告（5/1～5/8）皆有同樣症狀

---

## 二、根因

`reporter/templates/report.html` line 68-72 的 CSS：

```css
html, body {
    overflow-x: hidden;
    width: 100%;
    -webkit-overflow-scrolling: touch;
}
```

LINE in-app browser（iOS WKWebView / Android Chrome WebView）將 `html` 元素視為 viewport scroll container。當 `html` 設 `overflow: hidden`（即使只是 `overflow-x`），在某些 WebView 實作中會停止轉發 touch scroll 事件到 viewport → 整頁無法滑動。

W3C CSS spec 規定：`html` 與 `body` 的 overflow 互動有特殊 propagation 規則 —— 若 `html` 為 `visible`（預設），`body` 的 overflow 會 propagate 到 viewport；若 `html` 設為非 `visible`，`html` 自身成為 scroll container。LINE WebView 對「html 成為 scroll container 但被設 hidden」這個矛盾狀態的處理是「停止接收 touch」。

參考：
- WebKit bug #153852（overflow:hidden on html disables touch scroll）
- 多篇 LIFF 開發者社群回報

---

## 三、為何拖到 P70.3 才修

**「以為」清單**：

1. P63.2 引入移動版優化時，假設 `overflow-x: hidden` 是無害的安全網（防水平 scrollbar）。
2. 桌面瀏覽器與 Chrome Android 表現正常 → 假設「修補就 OK 了」，未開 LINE 實機驗收。
3. P63.4 / P64 / P65 / P67 等多次改 template，每次都讀到 `html, body { overflow-x: hidden }` 規則但**從未質疑**，因為它「看起來合理」且無回報。
4. 主公在 P63.2 後即發現 LINE 滑不動，但因症狀只在 LINE 出現、其他環境正常，被列為「P63.2 遺留小問題」延後到 P70.3。

**根本失誤**：UI/UX 修補沒在所有目標環境（含 LINE WebView）做 smoke test 就收官。

---

## 四、修法

兩部分（治本 + 治標）：

### 治本（template，影響未來新報告）

`reporter/templates/report.html`：
- 拆 `html, body {}` → 獨立 `html {}` + `body {}`
- `html {}` 只保留 `width: 100%`（移除 `overflow-x: hidden` 與 `-webkit-overflow-scrolling`）
- `body {}` 保留 `overflow-x: hidden` + `-webkit-overflow-scrolling: touch`
- `body {}` 新增 `touch-action: pan-y`（明示 LINE WebView 允許垂直 pan）

### 治標（已生成的舊報告）

對 `data/reports/aov_report_2026-05-*.html` 共 10 個主版報告套用相同 CSS 修補（Python 批次替換腳本，idempotent）。

## 五、可逆性

**X1 = 完全可逆**。純 CSS 修改，git revert 即還原；無 schema、API、部署副作用。

---

## 六、為什麼不寫 Playwright LINE WebView 自動化測試

- LINE in-app browser 無法直接用 Playwright/Selenium 自動化測試（WebView 環境受 LINE app 控制，無法獨立啟動）
- iOS WKWebView / Android Chrome WebView 雖可獨立測試，但與 LINE 的具體實作有差異
- ROI 不高：人工 1 分鐘可在 LINE 點開報告驗證；自動化建構成本高（需 LINE Developer 帳號 + LIFF app 設定 + Appium 之類框架）

**替代方案**：將「LINE 實機 smoke test」列為 UI/UX 變動的人工 SOP（見下節）。

---

## 七、防範措施

1. **新 SOP**：UI/UX 修補（任何動 `reporter/templates/` 的 Phase）收官前必須**主公在 LINE 實機點開驗收 1 個樣本報告**。寫入 `CLAUDE.md` 行為準則或 `feedback_workflow` 記憶。
2. **G2 認知防火牆強化**：「我以為 CSS 在所有環境都 OK」加進「我以為清單」，下次改 `overflow` / `position: fixed` / `touch-action` 等屬性時主動提示需 LINE 實機測試。
3. **G5-1 退化偵測**：`-webkit-overflow-scrolling: touch` 為 iOS 13+ deprecated 屬性，標記 90 天 review 期（到期日 **2026-08-08**）。
4. **X3 邊界**：本次修補的根因與 LINE WebView 行為有關，若 LINE app 重大改版（例如改用新 WebView 架構），修補可能失效或不再必要 —— 重大 LINE 版本更新時應重新驗收。

## 九、補錄事件 — `index.html` 本機破壞險些 push（2026-05-08 主公提醒「landing page 還是不見」後發現）

**事件**：對 `index.html` 套用 X2 預防性 CSS 修補時，未察覺該檔在 session 一開始的 `git status` 就已經是 modified 狀態（內容含**本機破壞** —— 5 個歷史報告連結被改為 `href="#"` 顯示「暫無歷史報告」）。直接在這個破壞版上加 CSS 修補後，差點隨 commit/push 把破損版蓋掉線上原本完整的 landing page。

**發現契機**：主公主動回報「landing page 還是不見了」→ 重新看 `git diff index.html` 才發現本機含大量非 CSS 改動。

**處置**：`git checkout HEAD -- index.html` 還原 → 重新對線上版套 CSS 修補 → `git diff` 確認只剩拆分 html/body + touch-action 兩處變動。

**根本失誤**：
1. **未驗證 modified 檔案的初始內容**：session 開頭看到 `M index.html` 但沒 `git diff` 看具體變化，預設「就是乾淨的本機版」就動工。
2. **63 維度稽核裡 X2 盲區掃描提到 index.html，但只查了「是否有相同 CSS 問題」，沒查「本機 working copy 與 HEAD 的差異是否含其他破壞」**。

**G2「我以為清單」追加**：
> 「我以為 modified 檔案的本機改動都是合理的、與當前任務相容」 → 錯。每次 session 開頭看到 `git status` 中 modified 檔案，**動工前先 `git diff <檔>`** 看內容；若含與當前 Phase 無關的改動，先決定保留/丟棄/單獨 commit，不要在它上面疊修補。

**X1 可逆性確認**：本次事件未 push，全程在本機可逆 → 嚴重度 = 中（險些 commit/push 但及時被主公揪出）。

**衍生待查**：本機 `index.html` 的破壞性連結變動是何時、哪個流程造成？候選原因：
- 某次本機跑 `python main.py` 時 `_update_landing_page` 呼叫，但對應 reports 檔當時不存在 → 連結 fallback 為「暫無」
- 之前某 session 手動測試遺留
- 列入 P70.5' 或獨立小 Phase 排查（main.py `_update_landing_page` 的 fallback 邏輯是否合理）

## 十、P70.3.1 流程失誤補錄（63 維度審計補做 + R-007/R-008 修補）

**事件**：P70.3.1（報告頁回首頁按鈕）動工時，沒有跑完整 63 維度 + 3 Patch 稽核就直接進入實作。主公事後發問「我們有做過 63 維度 + 3 Patch 的優化嗎？」才補跑審計，發現兩個遺漏：

- **R-007**：`.back-to-landing` 未加入 `@media (max-width: 768px)` 的 `backdrop-filter: none` selector → mobile 仍觸發模糊效果，增加滑動卡頓風險。
- **R-008**：缺少 `:focus` 可見輪廓（鍵盤/螢幕閱讀器無障礙）+ 缺少 `aria-label`（螢幕閱讀器語義不完整）。

**修補動作**（2026-05-08 補做）：
- `reporter/templates/report.html`：selector 加 `.back-to-landing`；補 `:focus` CSS；補 `aria-label`
- `data/reports/aov_report_2026-05-{01..10}.html`：idempotent 批次 Python 腳本同步修補（10/10 OK）

**根本失誤**：
1. **每個 P##.# 子 Phase 都需要獨立稽核**，不能因為是「衍生小 Phase」就預設豁免 63 維度流程。
2. 主動標誌：本 Phase 觸發了「UX 按鈕新增」→ UX 層（Patch-2）+ A11y 層（L9）都是必過項，動工稽核計畫書要明列。

**G2「我以為清單」追加**：
> 「我以為 P##.# 子 Phase 只是補丁，不需要完整稽核」→ 錯。任何新增 UI 元件的子 Phase，無論規模，都必須過 L1（代碼）/ L2（邏輯）/ L4（測試）/ L9（UX/A11y）/ L10（安全）五層最小集。
