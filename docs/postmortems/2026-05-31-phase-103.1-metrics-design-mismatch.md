## 一、症狀

`~/.claude/skill_metrics.jsonl` 從未生成；11 個 `.agent/skills/*/` 的 metrics 一直是空（SKILL_HEALTH 的 O1/O2/O3 永遠顯示 `--`）。

---

## 二、根因（兩層）

### 2.1 表層：Claude Code hooks 記不了
- `PostToolUse` 的 `matcher:"Skill"` 目前不觸發（官方 issue #43630）。
- payload 無 `skill_name`（issue #22655「不規畫」）。
- Stop hook 要自己解析 transcript（無 duration、成本高）。

### 2.2 更根本：skill 根本不以程式執行
AOV 的 `.agent/skills/*/__main__.py` 是手動 CLI 工具（`py __main__.py "query"`），`record()` 接在 `_run_with_metrics()` 的 `if __name__=="__main__"`。但這些 skill 實際**多是「對話內由 Claude 讀 SKILL.md 模擬觸發」，不是 shell 跑程式** → 根本沒有執行點可記 metrics。

---

## 三、「我以為」清單（G2-3）

1. **以為** metrics 空 = import 接線 bug → hooks 可修；**實情**是 skill 不以程式執行 → hooks 也救不了。
2. **以為** `record()`+`__main__` 接線壞了；**實情**接線沒壞，是「設計前提（CLI 程式）vs 實際用法（對話模擬）錯配」。
3. **以為** 移植 skills-governance 的 metrics.py（宣稱修了 `__main__` guard 根因）就能解；**實情**它只解「移除 __main__ guard」這一種失效，解不到「對話觸發時 Python 根本不執行」的真根因。

---

## 四、裁示與修法

**主公裁示（2026-05-31）**：關閉 R-024，承認設計限制——不強行做做不出來的 hooks 方案。
- R-024 從 RISK_REGISTRY 的 Open 移至 Closed，標 accepted 設計限制。
- 保留 `tests/test_skill_metrics_logger.py::TestImportDoesNotTriggerRecord` 錨點測試防悄悄恢復。
- 接手者若要 metrics，需另議觸發機制重設計（屬工具鏈/部署層，非引擎 scope）。

## 五、通則化教訓（G6）

> **「移植他處的『根因診斷』不能照搬結論，要先驗證目標環境的實際前提。」**

藍圖（G0 §六意外收穫）在 skills-governance 環境診斷出「metrics 空 = `__main__` guard 不觸發」，但回填到 AOV 時，AOV 的實際前提（skill 以對話模擬觸發、非 shell 執行）與該診斷的隱含前提（skill 是被執行的 CLI 程式）不同。Evidence-first 在動筆寫 hooks 計畫書前就擋下了這個錯誤方向——驗證目標環境的實際執行模型，比照搬他處結論重要。
