# Postmortem — P106.2：combat_stats 假戰績長期呈現（誠實紅線 + 假數據壓制 guard）

- **日期**：2026-06-07
- **Phase**：P106.2（combat_stats 假戰績誠實化，飛輪版）
- **性質**：Blameless postmortem — 誠實紅線 + 「我以為...結果不是」(G2-3) 事件
- **嚴重度**：中（報告長期用醒目儀表板呈現假戰績給阿喜，但 P106.2 飛輪根治 + 裝防復發護欄）

## 背景

每日戰報的「戰績儀表板」長期顯示芽芽 win 52.8% / pick 18.5%(或12.5%) / ban 45.2%，且 win>52 還 pulse-high 紅光高亮。阿喜以為是真實台服勝率。P106 計畫書（問題 2）早記載「芽芽勝率沒動」，但當時只查到 `sentiment.py` showcase 寫死值（pick=18.5），收尾未動。

## 時間線

1. 阿喜接 P106-2，memory 留謎題「dry-run pick_rate=12.5 ≠ 寫死 18.5」。
2. Claude 追資料流，發現**雙假數據源**：production 走 `hero_stats.py` 的 `# 模擬數據`（pick=12.5）、showcase 走 `sentiment.py` 寫死（pick=18.5）。破解 12.5≠18.5 謎題。
3. 更發現 `hero_stats.py` docstring 謊稱「從 Garena 官方排行榜抓取」、import httpx，但 `fetch_watchlist_stats()` 零真實請求——**combat_stats 從來沒真爬過**。
4. 阿喜問「能否取得真實數據」→ PoC 實測：Garena 官方勝率子域 `herowinrate.moba.garena.tw` 已下線（tw/vn/th 全 NXDOMAIN）、無 API、第三方只導流、遊戲內 API 逆向違 ToS+封號。
5. 阿喜二次追問「更好的做法」+ 點名飛輪 → 進飛輪模式 → 選方案 D 飛輪版（半自動真數據 + checker + data_source）。
6. 阿喜親自提供真值（芽芽 T1 51.2/13.41/36.32 不分段位）→ 凍結 → 外包 Antigravity Gemini 3.5 Flash(High) 實作 S1-S6 → Claude 審核（補 tier + 清越界/副作用）。

## 根因

1. **`hero_stats.py` 整個是 mock**：偽裝成 scraper（docstring + httpx import），實則回傳寫死 dict，從未真爬。
2. **P106 查根因只查一條路**：只查到 showcase（18.5），漏了 production 主路徑 mock（12.5），導致 memory 出現「12.5≠18.5」矛盾、修復一直沒到位。
3. **假數據壓制了一個 guard**：`history.py` 的「勝率 <47% 預警」因假數據固定 52.8% **永遠觸發不了**，這個 guard 死了很久沒人發現。

## 為何沒早抓到

假數據值「看起來合理」（52.8% 接近真實勝率區間），不像明顯 bug。且 P106 計畫書查根因時只 grep 到第一條（showcase）就收尾，沒查盡 production / fallback / showcase 所有生產路徑。

## 修法（P106.2 飛輪版）

1. `hero_stats.py` 移除 mock、改 `yaml.safe_load` 讀 `configs/hero_combat_stats.yaml`（阿喜手動維護真數據）、加 `data_source` 欄位、誠實 docstring。
2. 模板顯示真值 + 「真實官方數據・更新於 X」+ 熱度 tier + stale 過期警示 + 無資料空態 + showcase「演示數據」標籤。
3. **data_source 貫穿**：`history.py` 勝率預警改 `data_source=="manual_yaml"` 才觸發（救活死掉的 guard）；manifest `_meta` 記 source/age_days。
4. **反假數據 checker** `scripts/check_no_fake_stats.py`（advisory，掃 production 檔偵測寫死戰績潛入）。
5. 7+1 端到端測試；全套 489→496 passed 零回歸。

## 教訓與通則化

### B-025（新 blindspot，全域連續編號）

> **(a) 查寫死值/假數據的根因，必須查盡所有生產路徑（production + fallback + showcase），不可只查第一條就收尾**（P106 只查 showcase 漏 production mock，導致修復懸宕 + memory 矛盾）。
> **(b) 假數據不只騙使用者，還會讓依賴它的下游 guard 靜默失效**——移除/修正假數據時，要檢查是否有 guard 一直被假數據壓制（本 Phase：history 勝率預警因假數據 52.8% 永遠觸發不了，死很久）。修真數據後要驗證這些 guard 重新生效。

具體檢查點：
- 改/查寫死值前，`grep` 該值/欄位在**所有**寫入點（production 主路徑、fallback、showcase、demo），逐一確認哪條是 production 真正走的。
- 移除假數據後，搜尋所有「消費該數據做判斷」的下游（預警/gate/分支），確認它們在真數據下行為正確（假數據可能讓條件永遠真/假）。

## 防復發

- `scripts/check_no_fake_stats.py`（advisory checker）成為長期 guard，偵測未來寫死戰績潛入 production。
- `data_source` 標記讓報告/archive/預警全鏈可追溯數據真假。
- B-025 待 `cross-phase-review` / `blindspot-tracker` 評估是否納入 PHASE_TEMPLATE 開工檢查。
- 半自動真數據（yaml + stale 警示）取代假數據，過時數據誠實自曝而非偽裝即時。
